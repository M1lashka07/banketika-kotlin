## Быстрый запуск

Нужен **JDK 21 или новее**. Обычная Java 8 не подходит. Gradle отдельно устанавливать не нужно: wrapper включён в репозиторий.

1. Откройте папку проекта в IntelliJ IDEA или Android Studio как Gradle проект.
2. Выберите установленный JDK 21+ для Gradle и Project SDK.
3. Скопируйте `.env.example` в `.env` и заполните URL проекта и **publishable** ключ Supabase. В исходной рабочей папке `.env` уже настроен.
4. Запустите `main` в `Application.kt` или выполните команды ниже.

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-21'
.\gradlew.bat run
```

Адрес по умолчанию: **http://localhost:8080**. Сервер слушает только локальный компьютер (`127.0.0.1`). Для папки с кириллицей в Windows рекомендуем запускной скрипт: он размещает кэш и результаты сборки во временной папке с ASCII-путём, устраняя ошибку classpath тестового worker Gradle.

```powershell
.\scripts\run.ps1 -JdkPath 'C:\path\to\jdk-21'
.\scripts\run.ps1 -JdkPath 'C:\path\to\jdk-21' -Test
```

На macOS/Linux: `JAVA_HOME=/path/to/jdk ./gradlew run` и `./gradlew test`. Сервер автоматически читает `.env`; переменные окружения имеют приоритет. `APP_URL` должен совпадать с адресом в браузере. Для HTTPS установите `COOKIE_SECURE=true`.

## Пять основных страниц

| Адрес | Назначение |
| --- | --- |
| `/` | Регистрация: ФИО, телефон, **логин**, пароль; первая страница гостя |
| `/login` | Вход по **логину и паролю**, ссылка на регистрацию |
| `/cabinet` | Профиль текущего пользователя и только его банкеты |
| `/banquets/new` | Название, место, будущие дата и время по Москве, способ оплаты |
| `/admin` | Все заявки и пользователи, статусы, удаление и создание за пользователя внутри панели |

Email в формах и профиле **не используется**. Логин обычного пользователя: 3–32 латинских символа, цифры, точка, дефис или подчёркивание; регистр не учитывается. Пароль: 8–128 символов. Пароль администратора задан инициатором проекта и в репозитории не хранится.

Способы оплаты ровно два: «Наличными» и «Картой». Это запись выбранного способа, реальный эквайринг не подключён. Новая заявка всегда «На рассмотрении». Администратор может переключать её между «На рассмотрении», «В работе» и «Завершена». Удаление требует подтверждения прямо в карточке заявки и удаляет запись из базы.

## Настройка новой Supabase базы

Для уже подключённого проекта схема и администратор готовы. Для нового проекта:

1. Создайте Supabase проект и примените **`database/schema.sql`** в SQL Editor с правами владельца. Таблицы `profiles` и `banquets` доступны Data API только с предусмотренными grants и RLS.
2. В **Authentication → Sign In / Providers → Email** оставьте **Enable Email provider = ON**, установите **Confirm email = OFF**, сохраните. Обычная регистрация выполняется поддерживаемым `/auth/v1/signup`, пароль проверяется `/auth/v1/token?grant_type=password`.
3. Возьмите URL и publishable key из настроек проекта, запишите их в локальный `.env`.
4. Зарегистрируйте на сайте аккаунт с логином `admin26` и выбранным паролем. Назначьте его администратором SQL-командой ниже. После входа через псевдоним `admin 26` Auth проверит пароль того же аккаунта.

```sql
insert into private.administrators(user_id)
select id from public.profiles where login = 'admin26'
on conflict do nothing;
```

Чтобы отозвать права, удалите соответствующую запись из `private.administrators` через SQL Editor владельца. Проверка роли обращается к таблице при каждом защищённом запросе, поэтому не зависит от редактируемой пользователем metadata или старого JWT claim. Новые обычные аккаунты никогда не получают роль администратора автоматически.

Supabase Auth технически работает с внутренним идентификатором вида `логин@banketika.example` (зарезервированный служебный домен). Он не показывается в UI, не собирается у пользователя, не является контактным email и не используется для отправки писем. Именно поэтому подтверждение email отключено. При неверной настройке сайт не выдумывает сессию и сообщает, что аккаунт пока не активирован.

`database/login-registration.sql` — **историческая миграция** первоначального профиля с email на логин. На свежую схему из `schema.sql` её применять не нужно. `database/bootstrap-admin.sql` — однократная первоначальная подготовка фиксированного учебного администратора владельцем БД; для дальнейших аккаунтов используйте сайт и назначение роли выше. Ни один привилегированный RPC создания аккаунтов не открыт для анонимных запросов.

## Безопасность и права

| Операция | Гость | Пользователь | Администратор |
| --- | --- | --- | --- |
| Регистрация и вход | Да | Выход и повторный вход | Выход и повторный вход |
| Просмотр профилей | Нет | Только собственный | Все |
| Просмотр заявок | Нет | Только собственные | Все |
| Создание заявки | Нет | Только за себя | За любого зарегистрированного пользователя |
| Изменение статуса | Нет | **Никогда** | Да, только три разрешённых значения |
| Изменение владельца/полей существующей заявки | Нет | Нет | Нет; редактируется только статус |
| Удаление заявки | Нет | Только собственной | Любой |

Сервер передаёт в Data API **JWT текущего пользователя**, а не service role. Обычная форма создания игнорирует присланные `owner_id` и `status`; владелец берётся из подтверждённой сессии. На уровне базы колоночные grants запрещают явно задавать статус при INSERT и менять владельца при UPDATE; RLS UPDATE разрешает статус только администраторам. RLS закрывает чужие профили и заявки независимо от серверной проверки.

В браузере находится только случайный ID сессии в cookie `HttpOnly; SameSite=Lax` (и `Secure` при HTTPS). Access/refresh токены хранятся на сервере и обновляются под Mutex. При входе ID и CSRF меняются. Все POST формы защищены CSRF и проверкой Origin; HTML экранируется, действует CSP. Пароли, токены и тела Auth запросов не пишутся в журнал.

Сессии хранятся в памяти одного JVM процесса: после перезапуска требуется повторный вход. Банкеты и профили сохраняются в Supabase. Для нескольких экземпляров сервера понадобится общий session store; для учебного локального запуска это не требуется. Сброс пароля по email не реализован, поскольку email не собирается; администратор проекта может управлять аккаунтами в Supabase.

## Структура

```text
src/main/kotlin/ru/banketika/
  Application.kt   — маршруты, серверные права, CSRF, ошибки
  Config.kt        — конфигурация .env и окружения
  Models.kt        — модели и проверка введённых данных
  Supabase.kt      — Auth и PostgreSQL Data API
  Sessions.kt      — приватные сессии и обновление токенов
  Views.kt         — HTML всех пяти страниц на Kotlin
src/main/resources/static/ — CSS, JS и SVG
src/test/kotlin/ru/banketika/ — тесты форм, маршрутов и Auth gateway
database/ — SQL схема, миграция и первоначальная подготовка
scripts/ — Windows запуск и настоящие интеграционные проверки
docs/verification.md — результаты выполненных проверок
```

POST маршруты: `/register`, `/login`, `/logout`, `/banquets`, `/banquets/{id}/delete`, `/admin/banquets`, `/admin/banquets/{id}/status`, `/admin/banquets/{id}/delete`. `/health` возвращает `ok`. Дополнительных основных страниц нет.

## Проверки

Автоматические тесты: `./gradlew test` (в Windows с кириллицей используйте `scripts/run.ps1 -Test`). Они не требуют живой базы или секретов.

Опциональные **реальные** проверки: запустите сайт, затем `python scripts/live-check.py`. Скрипт спросит пароль администратора скрытым вводом либо прочитает `ADMIN_PASSWORD` из окружения. Он создаёт два временных QA аккаунта, проверяет Auth, серверные маршруты и прямые запросы с разными JWT; все созданные банкеты удаляет. Список QA пользователей сохраняется локально в `.runtime/live-report.json` для удаления владельцем проекта через Supabase. Выполняйте только в отдельном учебном проекте. Отчёт не содержит паролей, cookie или JWT.

`.env`, `.runtime`, `.tools`, кэши и результаты сборки исключены из Git. **Service role/secret key приложению не нужен.** Не добавляйте такие ключи в клиентские файлы или GitHub.

Официальные источники: [Ktor HTML DSL](https://ktor.io/docs/server-html-dsl.html), [Kotlin releases](https://kotlinlang.org/docs/releases.html), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Supabase Auth](https://supabase.com/docs/guides/auth/passwords).

Перенос на компьютер колледжа и отличия версии с MySQL/phpMyAdmin описаны в [инструкции](docs/college-transfer.md).
